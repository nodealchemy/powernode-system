## Domain Audits & Remediations

### Node lifecycle + cloud/VM providers

**Domain id:** `node-lifecycle-providers` &nbsp;•&nbsp; **Completeness score:** 62/100

The Node lifecycle + cloud/VM providers domain shows a functional state machine and bootstrap flow, but has significant operational gaps in error recovery, observability, and cloud provider completeness. Critical issues include missing transaction boundaries causing orphaned instances, absent sync_status implementations in major cloud providers (AWS/GCP/Azure/OpenStack) preventing state reconciliation, no FleetEvent emission for provisioning observability, and incomplete cloud-init/bootstrap token integration across providers. Test coverage is thin (smoke tests only, no unit tests for ProvisioningService). The domain would benefit from transactions around instance creation, universal sync_status implementations, comprehensive observability, and idempotent provisioning with proper error recovery paths.

**Strengths**

- NodeInstance state machine is comprehensive and well-designed with clear two-phase transitions (operator-initiated intermediate states, worker runtime finalizers). AASM integration is clean.
- Bootstrap token flow is secure (single-use, TTL-bounded, SHA-256 hashed in DB) and properly separated from enrollment service. Enrollment can be either initial or refresh.
- LocalQemuProvider and ProxmoxProvider have complete lifecycle implementations with cloud-seed/fw-cfg integration and sync_status. These serve as reference implementations.
- Provider registry pattern is extensible and allows for transient adapter creation (via with_credentials) for credential validation without DB persistence.

**Evidence & impact (critical + high)**

- **Missing transaction boundaries in instance provisioning** — _critical / latent_bug_  
  Location: `server/app/services/system/provisioning_service.rb:51-102`  
  Evidence: NodeInstance.create! (line 51) happens before provider.create_instance (line 76). If cloud provisioning fails, the instance row remains in 'pending' state orphaned in DB. Only mark_errored! is called but no cleanup of the created but unprovisioned instance.  
  Impact: Orphaned instance records accumulate in the database. Operator must manually clean up. No idempotency on retries - each retry creates a new instance row with a different timestamp-based name.
- **Major cloud providers missing sync_status implementation** — _high / incomplete_feature_  
  Location: `server/app/services/system/providers/{aws,gcp,azure,open_stack}_provider.rb`  
  Evidence: AWS, GCP, Azure, and OpenStack provider classes lack sync_status method. Only LocalQemuProvider and ProxmoxProvider implement it. NodeInstancesController#reconcile_in_flight_statuses calls adapter.sync_status (line 284) but returns silently if method missing (line 283: 'next unless adapter.respond_to?').  
  Impact: In-flight instance states (pending/provisioning/starting) never sync status from cloud provider. Instances stuck in transitional states won't update to actual provider state. Operators blind to cloud-side failures.
- **No FleetEvent emission from provisioning pipeline** — _high / operational_gap_  
  Location: `server/app/services/system/provisioning_service.rb, bootstrap_service.rb, node_enrollment_service.rb`  
  Evidence: ProvisioningService, BootstrapService, and NodeEnrollmentService contain zero FleetEvent emissions. Disk image services emit events, but core provisioning doesn't. No audit trail for provision success/failure/timeout for operator observability.  
  Impact: Operators cannot track provisioning lifecycle in the fleet dashboard. No correlation chains. Critical path errors are invisible to monitoring. SystemFleetChannel subscribers get no real-time updates on provisioning progress.
- **No idempotency on ProvisioningService.provision_instance** — _high / latent_bug_  
  Location: `server/app/services/system/provisioning_service.rb:167-171`  
  Evidence: generate_instance_name uses Time.current.strftime(). If API call is retried, a new timestamp-based name is generated and a second NodeInstance.create! succeeds, creating duplicate instances. No find_or_create pattern or operation_id de-duplication.  
  Impact: API retries on transient network errors create duplicate instances. Billing charges duplicate. Operator confusion on which instance to use. No safety against distributed caller retries.

**Designed remediations** (8)

1. **Add transaction boundaries + idempotency to instance provisioning** — effort `M`, risk `low`
   - Resolves: Missing transaction boundaries in instance provisioning; No idempotency on ProvisioningService.provision_instance
   - Approach: Wrap NodeInstance.create! and provider.create_instance in ActiveRecord::Base.transaction. Replace time-based instance naming with operation_id deduplication via find_or_create_by(operation_id). On transaction rollback (provider quota error, provision failure), orphaned instance row is automatically rolled back. This prevents duplicate instances on API retries and ensures atomic create-or-fail semantics matching Powernode's transaction-first pattern.
   - Reuses: ActiveRecord::Base.transaction (Rails standard); provisioning_service.rb naming pattern `generate_instance_name`; Powernode's deduplication pattern used elsewhere (BootstrapService, ModulePublicationProcessor). The operation_id column already exists on NodeInstance (audit trail). BaseRecord#find_or_create_by (project standard).
   - Files touched: server/app/services/system/provisioning_service.rb (wrap provision_instance method body in transaction; replace time-based naming with find_or_create_by logic); server/db/migrate/[timestamp]_add_operation_id_uniqueness_index_to_node_instances.rb (add unique index on [node_id, operation_id] if not present)

### AI/MCP workload substrate: provisioning, serving, and orchestrating AI-driven agents at scale

**Current state**

The system extension is a complete infrastructure-as-code substrate for general-purpose NodeInstance provisioning and management, with strong AI/MCP agent orchestration primitives:

### Self-improvement and continual-development engine

**Current state**

The Powernode system extension implements a **partial closed-loop self-improvement infrastructure** with operational findings feeding back to skill evolution:

**1. Sensor→Signal→Decision→Learning Pipeline** (LIVE in `/home/rett/Drive/Projects/powernode-platform/extensions/system/server/`):
- **18 concrete sensors** in `app/services/system/fleet/sensors/` detect operational signals (drift, failures, SLO breaches, CVE exposures, SDWAN reachability, honeypot access) every 60s
- Each sensor emits typed `FleetEvent` signals with `kind, severity, payload, correlation_id`
- `DecisionEngine` binds signals → skill executors → action categories
- `FleetAutonomyService.gate_action!` applies intervention policies + per-module consent budgets (lines 176-223, file: fleet_autonomy_service.rb)
- Fleet Autonomy runs 7 monitor agents with 68 total intervention policies across 6 seeds files (cve_responder, runtime_manager, sdwan_manager, disk_image_manager, fleet_autonomy, topology_designer)
- 52 skill executors at `app/services/system/ai/skills/` orchestrate remediation

**2. Learning Extraction & Auto-Skill Mutation** (LIVE, file: `app/services/system/fleet/learning_extractor.rb` lines 1-115):
- `LearningExtractor.record_tick!` captures every decision outcome (signal_kind, action_category, gate decision, disruption_pct) as `Ai::CompoundLearning` rows
- When AUTO_EVOLVE_THRESHOLD (default 3) matching learnings accumulate for a single signal_kind, `auto_evolve_skill` is triggered (lines 61-84)
- Parent platform provides `SkillMutationService` (file: `/home/rett/Drive/Projects/powernode-platform/server/app/services/ai/self_improvement/skill_mutation_service.rb` lines 1-155) with 4 mutation strategies:
  - `learning_driven`: mutates from active CompoundLearning records tagged by signal_kind
  - `failure_analysis`: mutates from failed skill usage records grouped by error type
  - `challenge_derived`: mutates from high-scoring self-challenges
  - `peer_comparison`: mutates by comparing low-performing skills with peers in same category
- Mutations generate `Ai::SkillVersion` variants at `testing` status + auto-create 20% traffic A/B tests

**3. Consent Budget Enforcement** (file: `app/services/system/fleet/consent_budget_service.rb`):
- Per-module daily autonomy ceiling (`consent_budget_per_day` on `System::NodeModule`) blocks over-zealous auto-remediation
- Budget exhaustion routes action to `require_approval` regardless of policy (lines 187-199, fleet_autonomy_service.rb)
- 24h rolling window, atomic increment for concurrency

**4. Cross-Domain Pressure Exchange** (file: ARCHITECTURE.md §5):
- Fleet emits `system.capacity_pressure`, `system.fleet_error_pressure`, `system.region_busy:<region_id>` after every tick
- `TradingPressureSensor` in fleet reads sibling-extension pressure signals; `TradingAwareThrottle` defers non-critical fleet actions when aggregate ≥ 1.0
- Stigmergic signal bus (`Ai::Coordination::StigmergicSignalService` in parent platform) enables bidirectional cross-extension coordination

**5. Attribution Feedback Loop** (cited in ARCHITECTURE.md §6 + FLEET_SENSORS.md):
- `AttributeFailureExecutor` ranks likely failure causes from recent FleetEvents + assignment changes + promotions
- Operator confirms/rejects via `AttributionFeedbackService` → boosts confirmed pairs (1.5x), downweights rejected (0.7x) in next executor invocation
- Feeds `Ai::CompoundLearning` for refinement

**6. Improvement Recommender** (parent platform: `app/services/ai/learning/improvement_recommender.rb`):
- `TrajectoryAnalyzer` scans agent execution history for patterns → generates `Ai::ImprovementRecommendation` (provider_switch, timeout_adjustment, cost_optimization, etc.)
- Recommendations can be applied to reconfigure agents

**7. Ralph Loop Adaptation** (parent platform model: `app/models/ai/ralph_loop.rb`):
- Repeating autonomy loops with configurable `scheduling_mode` (manual, scheduled, continuous, event_triggered, autonomous)
- Can be bound to infrastructure missions + risk_contracts for adaptive provisioning
- Lifecycle: pending → running → paused → completed/failed/cancelled

### General-purpose extensibility + plugin architecture

**Current state**

The extension implements **4 clean, production-grade extension points**: (1) **Provider Registry** (System::Providers::Registry, lines 7-189 at `app/services/system/providers/registry.rb`): Factory pattern with PROVIDER_CLASSES hash mapping "aws"/"gcp"/"azure"/"openstack"/"proxmox"/"mock"/"local_qemu"/"pro_cloud" → adapter classes. Base contract in BaseProvider (lines 10-439) defines authenticate?, provider_type, instance/volume/image lifecycle, normalized status enums. Adding new cloud provider requires: (a) subclass BaseProvider, (b) register in PROVIDER_CLASSES via .register(type, class_name). Works for AWS, GCP, Azure, OpenStack, Proxmox today. (2) **Skill Executor DSL** (System::Ai::Skills::BaseSkillExecutor, lines 40-170 at `app/services/system/ai/skills/base_skill_executor.rb`): 52 concrete executors (cve_response, docker_provision, rolling_module_upgrade, etc.) inherit BaseSkillExecutor and declare skill_descriptor (name, inputs, outputs, requires_approval, invocation_mode) + binds_to (agent names). Unified execute() lifecycle validates inputs, audit-logs, dispatches to perform(), wraps errors. Agents auto-discover bound skills via SkillBindings registry. (3) **Sensor-Signal Pattern** (System::Fleet::Sensors::BaseSensor, lines 18-40 at `app/services/system/fleet/sensors/base_sensor.rb`): Sensors only implement sense() → array of {kind, severity, payload, fingerprint} signals. DecisionEngine routes signals by kind to intervention policies and skill executors. Clean read-side-only abstraction. (4) **ACME DNS Adapter Base** (Acme::BaseDnsClient, lines 35+ at `app/services/acme/base_dns_client.rb` + DnsProviderRegistry at `app/services/acme/dns_provider_registry.rb` lines 4-97): 7 providers (Cloudflare, Route53, GCP, DigitalOcean, Hetzner, Porkbun, OVH) with static PROVIDERS hash. Shared HTTP/verb machinery centralizes get/post/put/delete, JSON parsing, auth patterns. Signing adapters (Route53, OVH) override #request. Adding new DNS provider: (a) create subclass, (b) add entry to PROVIDERS hash with lego_id + required_fields. **Partial extension point**: TopologyStrategies (hub_and_spoke.rb, full_mesh.rb in `app/services/sdwan/topology_strategies/`) — strategy pattern exists (~8700 lines) but TopologyCompiler hard-codes which strategy to use; no TopologyStrategyFactory registry.

## Integrated Roadmap

**North star**

> Powernode system extension as a self-improving, AI-first infrastructure substrate: a general-purpose orchestration engine for dynamic AI/MCP agent networks across distributed compute, combining autonomous decision-making (sensor-driven fleet autonomy, CVE response, module lifecycle), closed-loop self-improvement (post-remediation validation, A/B skill evolution, outcome-driven capability promotion), and clean extensibility (GPU-aware scheduling, inference runtimes, MCP servers as managed modules, cross-peer skill composition). The system transforms from a state-machine-driven provisioner into an evolving, self-optimizing platform where infrastructure changes are driven by AI agents learning from operational signals, with MCP as the universal interface for skill composition and peer-to-peer capability discovery.

**Themes** (4)

- **Operational Completeness & Observability Foundation** — Close silent failures and placeholder metrics that block self-improvement. Fix placeholder ProjectMetricsCollector, add missing error recovery paths, implement missing observability (FleetEvent emission from dispatch failures), and optimize observability query efficiency. This layer is prerequisite for all downstream self-improvement and AI orchestration work—without accurate telemetry and error visibility, the autonomous decision loop has no ground truth.
- **AI/MCP Substrate Evolution** — Expand the platform from single-runtime (Docker/K3s) to multi-runtime orchestration capable of hosting diverse AI workloads: GPU-aware scheduling, managed inference servers, MCP servers as native module runtimes, and capability-driven peer discovery. This enables the platform to serve as a general-purpose substrate for distributed AI agent networks, not just infrastructure provisioning.
- **Closed-Loop Self-Improvement Engine** — Wire feedback from operational outcomes back to skill evolution. Implement post-remediation validation (re-sense to confirm fixes), A/B test evaluation (auto-promote winning skill variants), skill trust tier gating based on evals, and sensor configuration auto-tuning. This transforms the platform from 'humans write once, autopilot executes' to 'autonomous agents refine themselves based on evidence'.
- **Extensibility & Plugin Ecosystem** — Establish clean registry patterns for runtimes, topology strategies, skill schedulers, and capability brokers. Enable third-party extension of autonomy (new sensor types, new runtime adapters, cross-peer MCP server hosting) without code modification. This unlocks decentralized agent networks and domain-specific skill specialization.
